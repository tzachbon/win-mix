# Win Mix open-source readiness research

**Snapshot:** 2026-09-21; local baseline `main` at `6702036067b36ef3c2f9854a76eba73a99e979fc`. Findings below are verified facts; recommendations are proposals only.

## Baseline

- The [README](https://github.com/tzachbon/win-mix/blob/main/README.md) already documents product scope, requirements, install/use, known limits, build/test commands, and release steps. The [release workflow](https://github.com/tzachbon/win-mix/blob/main/.github/workflows/release.yml) runs only on `v*` tag pushes, then checks, builds, hashes, and publishes the installer. It does not validate pull requests or ordinary pushes.
- [`Licenses/`](https://github.com/tzachbon/win-mix/tree/main/Licenses) contains third-party notices. No app license, contributor guide, security policy, issue/PR template, or code of conduct is present; GitHub’s [community-profile API](https://api.github.com/repos/tzachbon/win-mix/community/profile) reports those files absent. GitHub’s [private-vulnerability-reporting API](https://api.github.com/repos/tzachbon/win-mix/private-vulnerability-reporting) returns `enabled: false`.
- GitHub says a repository without a license retains default copyright, so others may not reproduce, distribute, or create derivatives; GitHub recommends a root license file ([licensing guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)).

## Priorities

1. **License:** Propose plain MIT if broad reuse is intended and the owner confirms rights to first-party code/assets. It matches the two owned projects checked; SoundSwitch’s GPL-3.0 shows the alternative copyleft choice. Keep existing third-party notices. The app icon/assets were not audited, so this proposal is not applied.
2. **Onboarding:** Add a short root `CONTRIBUTING.md` with the existing SDK/Inno Setup prerequisites, deterministic test command, issue/PR path, and realistic review expectations. Link it from README.
3. **CI:** Add Windows pull-request and default-branch validation using existing deterministic tests; retain installer publishing on the existing tag-only workflow.
4. **Support:** If Issues are enabled, make them the single initial public intake. Add concise bug/feature templates. Bug fields: Win Mix version, Windows build, affected Sonar channel/output, repro, expected/actual. Avoid a response-time promise. Markdown templates are lower maintenance while YAML forms remain preview.
5. **Security:** Do not direct vulnerability reports to public issues. If accepting them, enable GitHub private reporting or publish another private contact path before adding `SECURITY.md`; GitHub’s [policy guidance](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/add-security-policy) calls for supported versions and a report route.

**Limits:** This checks repository text, workflow files, public GitHub metadata, and the cited comparison repos. It does not audit license compatibility, asset ownership, or Windows runtime behavior. Comparison links follow live default branches and may change.
